# Backend & RLS Testing Plan for HAKMDAR

This test plan validates that Row Level Security (RLS) and storage isolation work correctly in Supabase, guaranteeing that **Lawyer A cannot view, mutate, or delete records or documents belonging to Lawyer B**.

---

## Storage Folder Path Convention (Important for Frontend Uploads)

All uploads to the `case-documents` bucket **MUST** adhere to the following path format:

```text
<lawyer_id>/<file_name>
```

- **`<lawyer_id>`**: The Supabase Auth User ID (`auth.uid()`) of the logged-in lawyer.
- **`<file_name>`**: The unique file identifier / filename (e.g. `doc_<uuid>.pdf` or `<timestamp>_contract.pdf`).

> **Frontend Upload Example:**
> ```typescript
> const filePath = `${user.id}/${Date.now()}_${file.name}`;
> const { data, error } = await supabase.storage
>   .from('case-documents')
>   .upload(filePath, file);
> ```

## Verification Checklist

### 1. Profiles Table Isolation
- [ ] **SELECT own profile:** When authenticated as Lawyer A, `SELECT * FROM profiles WHERE id = '<UUID_A>'` returns Lawyer A's profile.
- [ ] **SELECT other profile:** When authenticated as Lawyer A, `SELECT * FROM profiles WHERE id = '<UUID_B>'` returns 0 rows.
- [ ] **UPDATE other profile:** When authenticated as Lawyer A, `UPDATE profiles SET full_name = 'Hacked' WHERE id = '<UUID_B>'` modifies 0 rows.

### 2. Clients Table Isolation
- [ ] **SELECT clients:** When authenticated as Lawyer A, querying `clients` returns only Lawyer A's clients. Lawyer B sees 0 of Lawyer A's clients.
- [ ] **INSERT with mismatched lawyer_id:** Attempting to insert a client with `lawyer_id = '<UUID_B>'` while authenticated as Lawyer A is rejected by RLS (`WITH CHECK (auth.uid() = lawyer_id)`).
- [ ] **UPDATE / DELETE other's client:** Lawyer A cannot update or delete any client created by Lawyer B.

### 3. Cases Table Isolation
- [ ] **SELECT cases:** Lawyer A only sees cases where `lawyer_id = '<UUID_A>'`.
- [ ] **CROSS-TENANT FOREIGN KEY:** Attempting to create a case linked to Lawyer B's client under Lawyer A's ID fails or violates relational constraints / RLS.
- [ ] **UPDATE / DELETE cases:** Lawyer B cannot close, edit, or delete Lawyer A's cases.

### 4. Documents Metadata Isolation
- [ ] **SELECT documents:** Lawyer A only sees document metadata where `lawyer_id = '<UUID_A>'`.
- [ ] **INSERT document metadata:** Inserting a document record with `lawyer_id = '<UUID_B>'` while logged in as Lawyer A fails.

### 5. Time Entries & Billing Isolation
- [ ] **SELECT time entries:** Lawyer B cannot view billable hours or hourly rates logged by Lawyer A.
- [ ] **SELECT invoices:** Lawyer B cannot view invoices generated by Lawyer A.
- [ ] **SELECT invoice items:** Lawyer B querying `invoice_items` gets 0 rows for invoices owned by Lawyer A (enforced via the `EXISTS (SELECT 1 FROM invoices ...)` subquery).
- [ ] **INSERT / DELETE invoice items:** Lawyer B cannot add or delete invoice items linked to Lawyer A's invoices.

### 6. Storage Bucket Isolation (`case-documents`)
- [ ] **Allowed file types:** Uploading `.pdf` and `.docx` succeeds. Uploading `.exe`, `.png`, or other disallowed types is rejected.
- [ ] **File size limit:** Uploading a file > 10 MB is rejected with an error.
- [ ] **Read storage object:** Lawyer A can download `case-documents/<UUID_A>/contract.pdf`.
- [ ] **Cross-tenant read:** Lawyer B attempting to read `case-documents/<UUID_A>/contract.pdf` receives `403 Forbidden` / 0 rows.
- [ ] **Cross-tenant upload/delete:** Lawyer B attempting to upload or delete an object under `<UUID_A>/...` is denied by RLS.
